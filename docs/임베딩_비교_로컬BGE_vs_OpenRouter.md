# 임베딩 방식 비교 — 로컬 BGE-M3 vs OpenRouter API

> 작성 2026-08-07 · 근거: 이 시스템에서 실측한 값과 코드
> 대상: `EMBEDDING_DEVICE` 설정을 `cpu`(로컬) 로 둘지 `api`(외부) 로 둘지

---

## 결론

**로컬 유지를 권고한다.** 이유는 두 가지이며, 둘 다 이 시스템에 고유한 것이다.

1. 외부 API 규격에는 **sparse 벡터를 담을 필드가 없어** 하이브리드 검색의 절반이 사라진다
2. 적재 시 **사내 문서 본문 전체(청크 10,777개)가 외부로 전송**된다

다만 API에 실제 장점이 있고(디스크·메모리·CPU·재적재 속도), 재적재 시간이 문제가 되면
**사내망에 BGE-M3 추론 서버를 두는 중간 경로**가 있다.

---

## 1. 현재 상태 (실측)

| 항목 | 값 | 확인 방법 |
|---|---|---|
| 실제 사용 중인 경로 | **로컬 CPU** | Qdrant 포인트에 sparse 벡터 존재 (58~62개 항목) |
| BGE-M3 모델 크기 | 4.3GB | 컨테이너 `hf_cache` 볼륨 |
| 리랭커 모델 크기 | 2.2GB | 〃 |
| 기동 시 모델 로드 | 임베딩 13초 + 리랭커 11초 = **24초** | 예열 로그 |
| 답변 소요 | 1.8 ~ 3.5초 | 실측 |
| 지난 전체 적재 | 263문서 / 10,777청크 · **10시간 31분** | `documents.indexed_at` 최소~최대 |
| BGE-M3 라이선스 | **MIT** (상업적 사용 가능) | 로컬 모델 카드 `license: mit` |

> ⚠️ 10시간 31분은 **적재 시작~종료 간격**이다. 파싱·OCR·재시도·대기가 섞여 있어
> 순수 임베딩 연산 시간이 아니다. 이 수치로 API 전환을 판단하면 안 된다.

### `.env` 설정이 무시되고 있었던 이유

```
backend/.env        EMBEDDING_DEVICE=api    ← 의도
docker-compose.yml  EMBEDDING_DEVICE: cpu   ← 컨테이너에 직접 주입 (이쪽이 이김)
```

`load_dotenv`는 이미 존재하는 환경변수를 덮어쓰지 않는다. 그래서 `.env`의 `api`는
읽히지도 않았고, 실제로는 계속 로컬로 돌았다. (2026-08-07에 `.env`를 `cpu`로 정정)

## 2. 핵심 차이 — sparse 벡터

이것 하나가 판단의 대부분을 결정한다.

### 코드상 반환값이 다르다

```python
def _embed_locally(text):          # EMBEDDING_DEVICE=cpu
    return {'dense': [...1024...], 'sparse': {token_id: weight, ...}}   # 둘 다

def _embed_via_api(text):          # EMBEDDING_DEVICE=api
    # API는 통상 dense 벡터만 반환하므로 sparse는 빈 딕셔너리 처리
    return {'dense': [...1024...], 'sparse': {}}                        # dense뿐
```

### 이건 OpenRouter의 한계가 아니라 규격의 한계다

OpenAI 호환 `/embeddings` 응답 규격에 sparse를 담을 자리가 없다.

```json
{ "data": [ { "object": "embedding", "embedding": [0.03, -0.21, ...] } ] }
```

BGE-M3가 sparse를 만들어내도 **전달할 통로가 없다.** 다른 OpenAI 호환 제공자로 바꿔도 같다.

### 사라지면 무엇이 안 되나

| 벡터 | 잡는 것 | 예 |
|---|---|---|
| Dense (1024차원) | **의미** | "발전용량" ≈ "설비 규모" |
| **Sparse** (문서당 58~62개 토큰) | **정확한 문자열** | `제2021-122호` · `대주별 선순위` · `48.552MW` |

현재 검색은 **sparse로 후보를 좁히고 → dense로 순위를 매기는** 하이브리드 구조다.
sparse가 없으면 dense 단독 검색이 되어, **허가번호·계약번호·공문번호 같은 정확한 식별자
검색이 크게 약해진다.**

계획 중인 **컨텍스트 헤더 주입**(청크 앞에 `[사업: 당진행복솔라]`를 붙이는 개선)도
sparse가 있어야 효과가 크다. 헤더에 사업명을 넣는다는 건 **그 토큰이 실제로 존재하게
만든다**는 뜻이고, 그걸 잡아내는 것이 sparse이기 때문이다.

## 3. 항목별 비교

| 항목 | 로컬 BGE-M3 | OpenRouter API |
|---|---|---|
| **Sparse 벡터** | ✅ 있음 | ❌ 없음 (규격 한계) |
| **데이터 외부 전송** | ❌ 없음 | ⚠️ 질의 + **적재 시 문서 전문** |
| 디스크 | 4.3GB | 0 |
| 메모리 | 항시 점유 | 없음 |
| 기동 시간 | 13초 | 0초 |
| CPU 부담 | 질의·적재마다 연산 | 없음 |
| 재적재 속도 | CPU 코어 수에 묶임 | 병렬 호출로 단축 가능 (미측정) |
| 저사양 서버 배포 | 어려움 (6.5GB + RAM) | 쉬움 |
| 비용 | 0원 | 호출당 과금 |
| 네트워크 장애 시 | 영향 없음 | **검색 불가** |
| 모델 교체 | 재다운로드 필요 | 설정 변경만 |
| 라이선스 | MIT (제약 없음) | 제공자 약관 |

## 4. 적재 시나리오 — 질의와 차원이 다르다

API 전환에서 가장 과소평가되는 지점이다.

```
질의 시 : 질문 한 줄만 전송          → "당진행복솔라 PF 대주단"
적재 시 : 청크 10,777개 전부 전송     → 사내 문서 본문 전체
```

전송 대상에 다음이 포함된다.

- EPC 계약서 일반조건 (67,634자)
- 주주간계약서 (138,570자)
- PF 자금인출 내역 (대주별 약정금액·금리)
- 발전사업 허가증·개발행위허가서 전문

**웹 검색(Tavily)을 기본 꺼짐으로 둔 이유가 "질문에 사업명이 담긴다"였는데,
적재는 그보다 훨씬 큰 노출이다.**

## 5. 비용

| 구성요소 | 비용 |
|---|---|
| BGE-M3 (임베딩) | **0원** — 로컬, MIT |
| bge-reranker-v2-m3 (리랭커) | **0원** — 로컬 |
| Qdrant · PostgreSQL · Redis | **0원** — 자체 호스팅 |
| gpt-4o-mini (답변 생성) | 유료 (질문당) |
| Tavily (웹 검색) | 무료 1,000크레딧/월 |

로컬 모델은 **돈 대신 하드웨어**로 낸다. 디스크 6.5GB, 상시 메모리, 질의당 CPU 연산.

## 6. 중간 경로 — 사내망 BGE-M3 추론 서버

sparse를 지키면서 API의 장점을 가져오는 유일한 방법이다.

```
지금  : Django 컨테이너 안에서 CPU 연산
대안  : BGE-M3 추론 서버(FlagEmbedding server · Infinity 등)를 별도 호스트에 띄우고
        sparse 를 포함한 커스텀 응답을 받는다
```

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 사내망 서버 | sparse 유지 · 데이터 미유출 · CPU 부담 이전 · GPU 시 재적재 대폭 단축 | 서버 1대 추가 관리 · 그 서버가 죽으면 검색 정지 |

**재적재 시간이 실제로 문제가 될 때** 검토할 선택지다. 지금 단계에서는 과잉이다.

## 7. 판단 기준

| 상황 | 선택 |
|---|---|
| **현재 (단일 PC · 사내 문서 · sparse 필요)** | **로컬 유지** |
| 재적재가 너무 오래 걸려 업무에 지장 | 사내망 BGE-M3 서버 검토 |
| 저사양 서버에 배포해야 함 + 문서가 공개 자료 | 외부 API 고려 가능 |
| 외부 API + 사내 계약서 | **권하지 않음** |

---

## 8. 아직 측정하지 않은 것

판단을 확정하려면 아래가 필요하다. 현재는 근거 없이 추정만 가능하다.

- [ ] **재적재 중 순수 임베딩 시간의 비중** — 10.5시간 중 얼마가 임베딩인지 모른다
- [ ] API 병렬 호출 시 실제 단축폭
- [ ] sparse 제거 시 검색 품질 저하 정도 (회귀 질문 세트로 A/B 측정 가능)
- [ ] bge-reranker-v2-m3 라이선스 (로컬에 모델 카드가 없어 미확인)

**권고**: 재적재 전에 **문서 20개 정도로 표본 적재를 돌려 단계별(파싱·OCR·임베딩·업서트)
시간을 측정**한다. 순수 임베딩이 2시간이면 로컬로 충분하고, 12시간이면 서버 분리를
고민할 만하다. 숫자를 보고 정하는 것이 맞다.

## 부록 — 전환 방법 (참고용)

두 곳을 모두 바꿔야 한다. 한쪽만 바꾸면 컨테이너 환경변수가 이긴다.

```yaml
# docker-compose.yml — backend, worker 양쪽
environment:
  EMBEDDING_DEVICE: api
```

```bash
# backend/.env
EMBEDDING_DEVICE=api
EMBEDDING_API_BASE=https://openrouter.ai/api/v1
EMBEDDING_API_KEY=<키>
```

전환 후에는 **반드시 전체 재적재**가 필요하다. 기존 벡터는 sparse를 포함한 로컬 임베딩
결과라, dense 단독 질의와 섞이면 검색 결과가 일관되지 않는다.

확인 명령:

```bash
docker exec re_backend python manage.py check_secrets   # EMBEDDING_DEVICE 확인
```
