# RES AI Agent — 이관·구동 가이드 (개발자용)

> 대상: 이 저장소를 넘겨받아 자기 PC/서버에서 구동하려는 개발자.
> 원본 문서 없이 **적재 완료된 코퍼스를 이식**받아 RAG를 바로 돌리는 절차다.
> 코퍼스 없이 앱만 띄우려면 5장을 건너뛰면 된다 (챗봇 검색만 빈 결과, 나머지는 정상).
> 협업 규칙: `docs/협업_작업규칙.md` · 전체 맥락: `docs/프로젝트_현황_요약.md`

## 0. 받아야 하는 것

| 경로 | 내용 |
|---|---|
| GitHub | 코드 전체 (private — collaborator 초대 필요) |
| 별도 전달 (zip) | `corpus_package_*.zip` — Qdrant 스냅샷 + PG 코퍼스 덤프 (약 139MB) |
| 각자 준비 | OpenAI API 키(gpt-5.6 계열), Docker Desktop, 디스크 여유 약 10GB |

zip에는 **사내 문서 본문이 그대로** 들어 있다. 사내 자료와 동일 등급으로 취급.

## 1. 클론 + 환경변수

```bash
git clone https://github.com/ht-082/RES-AI-Agent.git
cd RES-AI-Agent
cp .env.example .env                    # docker-compose 용 (DB 계정)
cp backend/.env.example backend/.env    # Django 용 (API 키 등)
```

`backend/.env`에서 반드시 채울 것:
- `DJANGO_SECRET_KEY` — 비면 기동 자체가 중단된다.
  `python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"`
- `LLM_API_KEY` — 본인 OpenAI 키
- `LLM_MODEL` / `LLM_VISION_MODEL` — 기본 `gpt-5.6-terra` 유지 권장.
  gpt-5.x는 추론 모델이라 `temperature=0`을 거부하고 `max_tokens` 대신
  `max_completion_tokens`를 쓴다. 코드가 이에 맞춰져 있어 4o 계열로 내리면 400 에러.
- 루트 `.env`와 `backend/.env` 양쪽의 `LLM_API_BASE`/`LLM_API_KEY`는 같은 값으로.

## 2. ⚠ 신규 설치 시 db/schema.sql 비활성화 (중요)

`docker-compose.yml`은 `db/schema.sql`을 postgres initdb에 마운트한다(20행).
**이건 마이그레이션 체계가 갖춰지기 전의 유산이다.** 지금은 마이그레이션이
bizdev 포함 전체 스키마(29 테이블)를 만들 수 있으므로, 신규 설치에서는
schema.sql을 쓰면 안 된다 — 실측 결과 `accounts.0002_alter_user_table`이
`relation "users" already exists`로 실패한다(schema.sql이 먼저 만든 users와 충돌).

신규 설치라면 **기동 전에 20행을 주석 처리**한다:

```yaml
    volumes:
      - pg_data:/var/lib/postgresql/data
      # - ./db/schema.sql:/docker-entrypoint-initdb.d/01_schema.sql:ro   # 신규 설치 시 비활성화
```

(기존 개발 PC처럼 이미 schema.sql로 만들어진 DB는 그대로 두면 된다.
`docs/협업_작업규칙.md` 3장에 두 체계 병행 시 주의사항이 있다.)

## 3. 기동

```bash
docker compose up -d
```

컨테이너 6개(`re_backend/frontend/postgres/qdrant/redis/worker`)가 뜨면 정상.
첫 기동 시 BGE-M3 임베딩 모델(~2GB)을 HuggingFace에서 받는다 — 인터넷 필요.
사내망 SSL 문제는 `README.md`의 "개발 메모" 참고.

## 4. 스키마 생성 + 계정

```bash
docker exec -it re_backend python manage.py createsuperuser
```

검증 (기대: 드리프트 없음):


## 5. 코퍼스 이식 (RAG 데이터)

전달받은 zip을 프로젝트 루트에 풀면 `corpus_package/`가 생긴다.

```bash
# 5-1. PG 코퍼스 (프로젝트·문서 메타·청크 본문)
docker exec -i re_postgres psql -U re_user -d re_agent < corpus_package/corpus_data.sql

# 5-2. Qdrant 스냅샷 (벡터 18,823개)
curl -X POST "http://localhost:6333/collections/re_documents_v2/snapshots/upload?priority=snapshot" \
  -F "snapshot=@corpus_package/re_documents_v2.snapshot"
```

두 파일은 **같은 시점의 쌍**이다. 한쪽만 다른 버전과 섞으면 청크 ID가 어긋나
"본문 없는 후보" 경고가 뜬다. (재생성은 `backend/make_corpus_dump.py` + 스냅샷 API)


## 9. 원본 문서로 직접 적재하려면 (코퍼스 이식 대신)

원본 파일을 `backend/media/initial_docs/{PJT폴더}/`에 두고:
```bash
docker exec re_backend python manage.py ingest_initial_docs --classify-only   # 분류 검토
docker exec re_backend python manage.py ingest_initial_docs --sync --corpus-version 2.0
```
**OCR 비용과 수 시간이 든다**(스캔본 68건·1,017페이지 실측). 이식이 가능하면 이식을 권한다.
`--type-map`은 옛 파일명 기준 CSV라 지금은 쓰지 않는다. `reset_db.py`류 전체 삭제 금지.

## 10. 이식 코퍼스의 알려진 한계

- **출처 칩의 "원문 열기"는 404** — 원본 파일(`media/documents/`)은 이관에 미포함.
  검색·답변 품질에는 영향 없음.
- DRM 잠금 4건(관리운영위탁 계약 2·EPC목적설계·당위성자료)은 원래부터 미적재.
- `약정서_대출_220531.pdf`(안면도 365p)는 보류 상태로 코퍼스에 없음.
- 사업개요 md 중 당진2·임자·안면도는 AI 초안(문서에 "원본 우선" 명시됨).

## 11. 이관 후 문서 추가·갱신

```bash
docker exec re_backend python manage.py refresh_doc --file "media/initial_docs/…"
```
결정적 청크 ID라 기존 코퍼스와 안전하게 합쳐진다. 상세는 `README.md`.
