## 2. 파이프라인 (큰 틀 유지)

```
[매직바이트 게이트] → 파싱(포맷별) → 머리말/꼬리말 제거 → 유형 분류(규칙→LLM)
   → 유형별 청킹 → 페이지/오프셋 매핑 → BGE-M3 임베딩 → Qdrant + Postgres
```

이미 구현 완료되어 유지하는 것: 머리말/꼬리말 위치기반 제거(`strip_repeated_edges`), 페이지 역산(page map, 31/31건 100% 검증), 분류 마커(`LAW_MARKERS`), 폴백 DB 기록(`chunking_fallback`), 프로젝트=최상위 폴더, checksum 접두 저장명(파일명 충돌 방지).

## 3. 파싱 전략 (포맷별)

### 3.0 공통 — 매직바이트 게이트 (신규)
파싱 전에 파일 서명을 확인한다. `PK`(zip계열: docx/xlsx/pptx/hwpx), `%PDF`, `D0CF11E0`(ole2: hwp)만 각 파서로 보낸다.
- 확장자와 불일치 → `status='failed'` + `metadata.fail_reason` 기록. **조용히 빈 텍스트로 적재되는 것을 금지.**
- **DRM 판별**: ole2 위장 파일에서 `FSD`/`EncryptedPackage`/`DRM` 마커 감지 시 `fail_reason='drm-protected'`로 구분 기록 — 파서 문제가 아니라 **권한 문제**임을 명시해, 재수급 대상 목록을 DB에서 바로 뽑을 수 있게 한다. 복호화 우회는 시도하지 않는다(사내 보안 통제).
- **그룹웨어 래핑 복구**: 확장자가 pdf인데 서명이 다르면 파일 내 `%PDF` 오프셋을 탐색, 있으면 그 지점부터 읽어 정상 파싱한다 (핸디소프트 전자결재 첨부 실측 1건 — 앞 429바이트 메타 뒤에 온전한 PDF). 전자결재 유출본은 앞으로도 나올 수 있어 일반화한다.

### 3.1 PDF (159건, 주력)
- **페이지 단위 유지** (fitz). 페이지당 중앙 703자로 청킹 단위로 적정.
- 스캔본(추출 50자 미만): **전량 Vision OCR로 처리** (✅ 사용자 결정 2026-07-17. 결정 전 저가치 스캔인 통장사본류는 사용자가 선별 삭제). 현행 `parse_with_vision_api` 유지 — 페이지별 `page_number` 반환(위치 매핑 호환), 표를 Markdown으로 추출(§3.6 정합), 429 재시도 내장.
  - 실측 규모: **45건 · 324페이지 → 약 1시간 · $1~3** (gpt-4o-mini vision, 페이지당 2초 대기 포함).
  - OCR 결과는 `metadata.ocr=true` 마킹 (추출 오류 가능성을 출처에서 식별하기 위함). 페이지 추출 실패 시 해당 문서 `failed` 처리.
  - 스모크 테스트: 발전사업 허가증 1건으로 추출 품질 확인 완료.
- 대형 PDF(600p급)는 그대로 처리하되 적재 시간에 반영 (§6).

### 3.2 DOCX (45건)
- 현행 유지: 5문단/800자 섹션 묶음. 단 **섹션 번호는 실제 페이지가 아님**을 메타에 명시 (`page_kind='section'`) — 출처 표기 시 "p.N"이 아니라 "섹션 N"으로 렌더링하기 위함.
- **표 청크의 page_number 충돌 수정**: 현행은 `section_idx + table_idx`로 본문 섹션 번호와 겹침. 표는 `section_title='표 N'` + 본문 마지막 섹션 이후 번호로 부여.
- 영문 계약(2건, 70만 자)은 `제N조`가 없어 general로 흐름 — §7.

### 3.3 HWP (72건, 2위 포맷)
- ✅ **hwp5txt(pyhwp) 채택** (검증 완료 2026-07-17): 정규식 실패 15건 중 **14건 구제**, 성공분에서도 현행 대비 **4~10배** 추출(예: 433→4,228자 — 정규식은 성공한 파일에서도 대부분을 유실하고 있었음). requirements.txt에 pyhwp 추가.
- 처리 순서: hwp5txt 우선 → 실패/미설치 시 정규식 폴백 → 최종 200자 미만이면 `hwp-extract-too-short`로 실패 처리.
- hwp는 페이지 정보가 없어 단일 항목으로 반환 (분할은 청커 몫, 출처 위치는 문서 단위).

### 3.4 XLSX (12건)
- 현행 유지 (시트별 30행 묶음). 실측 최대 1,109행이라 부담 없음.
- 전부 재무·집행현황류 — **재무모델의 인덱싱 가치 자체**는 §7 결정 사항 (기획서상 재무모델 기능은 보류 상태).

### 3.5 PPTX/HWPX (각 2건)
- 현행 유지 (슬라이드/섹션 단위, page_number 정상 추출 확인됨).
- pptx는 **표를 아예 읽지 않는 버그성 갭** 있음(텍스트 도형만 순회) — §3.6에서 함께 수정.

### 3.6 표 처리 — 구조 보존 직렬화 (신규)

현행은 모든 표를 `" | "` 이어붙이기로 평탄화 → **열 제목과 값의 연결이 끊겨** "대호1차 용량은?" 류 질의에서 값의 의미를 알 수 없다. 실측 결과 표 밀도가 높아(PDF 샘플 12건에서 57개, docx 15건에서 61개 — 계약서 대금표·허가 조건·공정률·대출조건) 구조 보존의 가치가 크다.

**직렬화 규칙 (공통)**
- 소형 표(≤15행): **Markdown 표** 통째로 청크화 (LLM이 구조를 그대로 이해).
- 대형 표(>15행): **헤더를 반복**하며 20행 단위로 분할 — 어느 청크든 자기설명적이 되게.
- 핵심형 표(재무·목록): 행 단위 서술화 병행 검토 (`사업명: 대호1차, 용량: 48.552MW, …`) — 청크가 잘려도 각 행이 완전한 의미 유지.
- 표 청크 메타: `metadata.kind='table'`, page_number는 표가 있는 페이지 그대로.

**포맷별 구현**
| 포맷 | 방법 | 비고 |
|---|---|---|
| PDF | **fitz `find_tables()`** (설치본 1.28 내장, 신규 의존성 없음) | 표 추출 성공 시 해당 영역을 본문 텍스트에서 제외(중복 방지), 감지 실패 시 현행 텍스트 유지(안전 폴백) |
| docx | python-docx 표 구조를 Markdown으로 직렬화 | 구조는 이미 받고 있었음 — 뭉개지만 않으면 됨 |
| xlsx | 첫 행을 헤더로 감지 → 행 서술화 | 30행 묶음 유지 |
| pptx | `shape.has_table` 분기 추가 | 현재는 표 유실 중 |
| hwpx | XML `<tbl>` 요소 파싱 (선택) | 2건뿐이라 후순위 |
| hwp/스캔PDF | 미지원 (구조 인식 불가) | — |

## 4. 분류 전략 — 6종 체계

**유형 신설 원칙**: 청킹 방식이나 메타데이터가 실제로 달라질 때만 유형을 만든다. (유형이 늘수록 분류 오류 표면적과 유지보수 비용이 함께 는다.) 이 기준을 통과한 것이 `spec`·`admin` 2종이며, 정기보고서(→report+날짜 메타)·입찰(무정형)·영문계약(→contract 청커의 패턴 확장, §7-3)은 통과하지 못해 만들지 않는다.

| 유형 | 대상 | 규모(실측) |
|---|---|---|
| `law` | 법령·고시·지침 | 12건+ |
| `contract` | 계약서 (제N조 구조) | 25건+ |
| **`spec`** (신설) | 시방서·과업지시서·계약조건 편별 문서 (`제N장/제N절` 구조) | ~51건 |
| **`admin`** (신설) | 공문·허가증·통보서·승낙·증명 (짧은 행정문서) | 35건+ |
| `report` | 보고·설명자료 (페이지/슬라이드형) | 16건+ |
| `general` | 그 외 | 나머지 |

### 규칙 (우선순위 순)
1. `law` — 현행 유지 (`제N조` 5회↑ + `LAW_MARKERS`). 오분류 0건 검증 완료.
2. **`spec`(신규)** — `제N장`/`제N절` 패턴 3회 이상 **또는** 파일명에 `시방서|과업지시|설계기준|Manual`.
3. `contract` — 현행 유지 (`제N조` + 갑·을 동시/당사자/체결).
3-1. **`contract` 영문(신규)** — 줄머리 `Article N`/`Section N(.N)`/`Clause N` 패턴 **합계 10회 이상** + `Agreement`/`Parties`/`hereinafter`/`shall mean` 중 1개 이상 → `contract` + `metadata.lang='en'`. (실측: Loan Agreement — Article 52·Section 139회, EPC — Article 158회. 영문 계약은 앞으로도 유입 예정이라 규칙화)
4. **`admin`(신규)** — 문서번호 패턴(`\d{4}-\d+`) 또는 파일명에 `공문|허가증|통보|승낙|신청서|접수증|증명|필증` + 텍스트 3,000자 미만. **현행 규칙 3의 "허가 통보→report" 오분류를 이 규칙이 흡수**하므로 report 규칙보다 먼저 평가한다.
5. `report` — 현행 유지.
6. LLM 폴백 — 프롬프트를 **6종으로 확장**하고 **파일명을 포함**한다("○○용역계약서.docx", "허가증" 등 파일명 신호가 강함). 239건 × gpt-4o-mini ≈ 수백 원, 1회성 비용으로 수용.

- **폴더명은 분류에 사용하지 않는다** (사용자 결정: 하위 폴더 분류가 부정확할 수 있음). 출처 추적용 `metadata.source_path`만 기록.
- **절차적 안전장치**: 본적재 전 `--classify-only` 드라이런 → `classification_result.csv`를 사람이 검수 (특히 LLM 판정분). 검수 결과는 `--type-map` CSV로 오버라이드.

## 5. 청킹 전략 (핵심 변경)

### 5.0 공통 목표
| 항목 | 값 | 근거 |
|---|---|---|
| 목표 청크 크기 | **300~800자** (≈180~480토큰) | 검색 문맥 확보 + 리랭커 max_length 512와 정합 |
| 최소 보장 | 300자 (병합으로 달성) | 세그먼트 84%가 300자 미만 → 병합 없으면 파편 재생산 |
| 최대 | 1,500자 초과 시 1,200자/오버랩 150자 하위분할 (현행 유지) | |
| 폐기 기준 | 최종 청크 20자 미만 | 1~15자 잡음 제거 |

### 5.1 law / contract — 조항 누적 병합 (신규)
현행 "조항 1개 = 청크 1개"를 "**조항을 순서대로 누적해 300자를 넘기면 청크 확정**"으로 변경.

```
buffer = []
for 조항 in 조항들(순서대로):
    if len(조항) > 1500:            # 대형 조항은 단독 + 하위분할 (현행)
        flush(buffer); 하위분할(조항)
    else:
        buffer.append(조항)
        if 누적길이(buffer) >= 300: flush(buffer)
flush(buffer)                        # 잔여
```

**경계 패턴 일반화 (단일 병합 엔진)** — 병합 로직을 `chunk_by_boundaries(text, 경계패턴셋, ...)` 하나로 구현하고, 문서 성격에 따라 경계 패턴만 바꿔 재사용한다:

| 대상 | 경계 패턴셋 |
|---|---|
| law/contract (한글) | `제N조(의N)` |
| **contract (영문)** | 줄머리 `ARTICLE 로마숫자` · `Article N` · `Section N(.N)` · `Clause N` · `N. 대문자제목` 중 **매칭 수가 가장 많은 패턴을 자동 채택** (가장 촘촘한 구조 단위가 병합 엔진과 최적 — 실측: Loan은 Section 139회≈2,400자/절, EPC는 Article 158회≈2,300자/절로 한글 조항과 같은 급) |
| spec | `제N장` → `제N절` (§5.4) |

한 엔진에 패턴셋 3종이므로 코드 중복 없이 영문 계약·시방서가 함께 해결된다. 한·영 병기 문서(실측 두 건 모두 20~24% 한글 혼재)는 지배적 패턴이 경계가 되고 나머지 언어는 청크 내용으로 자연 포함된다.

- 메타데이터: 병합 청크의 `article_no`는 범위 표기(`"제3조~제5조"`, `"Section 2.1~2.4"`), `metadata.articles=[...]`로 개별 목록 보존. `char_start`는 첫 조항 기준(페이지 역산 호환).
- `[전문개정 …]`·`[시행일 …]` 등 개정 이력은 본문에 유지 (노이즈 아님 — 감사에서 확인).
- law의 `version`(current/future) 분리: 시행일이 다른 조항은 **같은 청크로 병합하지 않는다** (신구조문 혼합 방지, 현행 취지 유지).
- 기대 효과: 법령·계약 청크 수 약 1/2~1/3로 감소, 파편(100자 미만) 61% → 사실상 0%.

### 5.2 report — 페이지 단위 + 소페이지 병합
- 페이지 단위 유지 (중앙 703자 적정).
- **100자 미만 페이지**(표지·간지·구분 페이지)는 다음 페이지에 병합. `page_no`는 병합 시작 페이지, `metadata.pages=[1,2]`로 범위 보존.
- `slide_title`(첫 줄) 추출 현행 유지.

### 5.3 general — 문단 경계 스냅
- 800자 목표는 유지하되, 절단 지점을 **가장 가까운 문단 경계(`\n`)로 후퇴**시켜 문장 중간 절단을 방지. 문단 경계가 없으면(연속 텍스트) 현행 기계 절단.
- 오버랩 150자 유지 (병합형인 law/contract는 조항 경계가 자연 문맥이므로 오버랩 불필요).

### 5.4 spec — 장·절 단위 병합 (신설)
- 분할 경계: `제N장` → `제N절` → (없으면 번호 항목). `제N조`용 조항 병합 로직(5.1)을 경계 패턴만 바꿔 재사용한다 — 누적 300자 병합, 1,500자 초과 하위분할 동일.
- 메타데이터: `chapter`(제N장 제목) · `section`(제N절 제목). `section_title` 표기는 `"제2장 제1절(일반시방)"` 형식.
- 장·절 경계를 넘는 병합은 하지 않는다 (시방서는 장이 곧 주제 경계).

### 5.5 admin — 문서 전체 단위 (신설)
- 짧은 행정문서(대부분 1~3쪽)이므로 **문서 전체를 청크 1개**로 한다. 3,000자 초과 시에만 페이지 단위로 분할.
- 메타데이터 추출: `doc_no`(문서번호, `\d{4}-\d+` 패턴) · `issued_date`(발급일) · 발신기관(추출 가능 시). "당진 1차 허가일이 언제야?" 류의 팩트 질의 대응이 목적.
- 병합·오버랩 없음.

### 5.6 xlsx — 유형 무관 시트 단위 라우팅 (신설, 버그성 갭 수정)
- 현행 tasks.py는 `report`만 파서 단위를 보존하고 나머지는 전체 텍스트를 합쳐 재절단한다. **xlsx가 general로 분류되면 시트 구조가 뭉개진 뒤 800자로 잘리는 문제.**
- 수정: **파일 확장자가 xlsx면 doc_type과 무관하게 파서가 만든 시트/30행 묶음을 그대로 청크로 사용** (pptx가 report로 가는 것과 동일한 원리를 포맷 기준으로 보장).

### 5.7 위치 메타 (유지)
`build_text_and_page_map` + `char_start` 역산 방식 그대로. 병합 청킹에서도 `char_start`(첫 조항 오프셋)만 넘기면 페이지 역산이 동작한다. 수정 후 `test_pagemap.py`·`test_chunking_audit.py`로 회귀 검증 필수.
