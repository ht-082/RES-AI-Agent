## A. 검색·근거 품질 (백엔드)

### A-1. Qdrant 하이브리드 검색 (dense + sparse) — ○
- **구현** `services/retriever.py` `ExistingQdrantRetriever._get_relevant_documents`
- sparse 로 Prefetch 후 dense 로 최종 정렬. BGE-M3 한 모델이 두 벡터를 동시에 낸다.
- **왜** 고유명사(SPC명·사업명)는 sparse 가, 의미 유사도는 dense 가 잡는다. 한쪽만 쓰면
  "당진행복솔라" 같은 사내 고유명사를 놓친다.
- **fork** 동일.

### A-2. 컨텍스트 헤더 주입 `[사업: X] [문서: Y]` — △ **(품질 저하 원인)**
- **구현** 적재 시 `apps/rag/tasks.build_embed_header` (임베딩 입력),
  질의 시 `services/retriever._rerank_context_header` (리랭커 입력)
- **왜** 문서명에만 신호가 있는 청크가 본문에 질의어가 없다는 이유로 밀렸다.
  **실측: `계약서_설계용역_251231.docx` 의 계약 당사자 조항이 0.117 → 0.835**
- **fork 문제** `_project_label_map()` 의 `Project.objects.all()` 에 `.using(db_alias)` 가
  빠져 **항상 기본 DB만 읽는다.** fork 기본 DB 는 비어 있어(실측 Project 0건 vs
  final_corpus 153건) 리랭커 헤더가 `[문서: …]` 만 남고 **`[사업: X]` 가 조용히 사라진다.**
- **영향(실측)** 리랭커 점수가 통째로 이동 → 게이트 상대컷 통과 건수가 바뀜.
  S1(설비용량 비교)이 통과 2건 → 1건, 답변이 "당진1 100MW·당진2 79MW" → "세 사업 모두 확인 불가".
  게이트 수치 전반 이동: N3 0.5103 → 0.5400 (차단 임계 0.55 에 근접).
- **주의** `_PROJECT_LABEL_CACHE` 가 모듈 전역 단일 캐시라 **한 번 비어 로드되면 프로세스 내내
  빈 채로 남는다.** alias 별 캐시로 분리해야 한다.

### A-3. 리랭커 (bge-reranker-v2-m3 · OpenVINO INT8 · max_length 384) — △
- **구현** `services/retriever.get_reranker` / `rerank_documents`
- 로짓에 시그모이드를 씌운 확률(0~1)을 `rerank_score` 로 남겨 게이트가 해석 가능한 값으로 판단한다.
- **왜 384인가** 768 과 4개 질의에서 순위가 전부 동일한데 지연은 절반(실측 6.1초 vs 14.7초).
  핵심 신호가 청크 앞머리에 몰려 있기 때문이다.
- **fork 문제** OpenVINO INT8 IR(`backend/.ov_reranker_int8`, 567MB)이 없어 **torch 로 조용히
  폴백**한다(`OpenVINO INT8 IR이 없습니다`). 측정 중 구 저장소 산출물을 복사해 임시 해결했으나,
  **fork `.gitignore` 에 `.ov_reranker_int8/` 항목이 없어** 다음 `git add` 때 567MB 가 커밋될 위험이 있다.
- **영향** 속도 저하 + 양자화 차이로 게이트 경계(0.55) 근처 점수가 흔들려 품질 판정까지 왜곡된다.

### A-4. 조건부 리랭킹 (`should_rerank`) — ○
- **왜** 리랭커는 질의당 수 초를 쓰는 가장 비싼 단계다. Qdrant 점수만으로 컨텍스트 경계가
  이미 명확하면(경계 점수차 / 전체 폭 ≥ `RERANK_SKIP_MARGIN` 0.25) 건너뛴다.
- **fork** 동일.

### A-5. 완전일치 중복 제거 (`dedupe_documents`) — ○
- **왜** 같은 내용 청크가 568종 존재해 컨텍스트 8칸 중 4칸을 잠식, 비교 질문이 실패한 사례가 있었다.
- **설계 의도** 근사 중복은 **일부러 묶지 않는다** — 서로 다른 사업의 유사 조항이 하나로 합쳐질 위험.
- **fork** 동일.

### A-6. 관련성 게이트 (2단 구성) — ○
- **구현** `services/retriever.apply_relevance_gate`
- ① 질의 게이트: 1위 < 0.55 면 전부 버리고 '자료 없음' ② 상대 컷: 1위 − 0.12 미만 꼬리 제거
- **근거** 질의 10건 실측에서 답 있음 0.6019~0.7310 vs 답 없음 0.5001~0.5179 로 깨끗이 갈렸다.
- **fork** 함수는 동일. 단 **뒤처리가 다르다 → A-7 참조.**

### A-7. 무근거 고정응답 (LLM 미호출) — ✗ **fork 없음**
- **구현** `apps/chat/views.py` — 게이트 탈락 시 `"관련 자료를 찾지 못했습니다."` 를
  **LLM 호출 없이** 즉시 반환 (구 저장소 2곳: 비스트리밍 411행 · 스트리밍 642행)
- **fork** 이 분기가 **0건**. 컨텍스트만 비우고 LLM 을 호출한다.
- **영향** ① 환각 위험 — 근거 0건인데 일반 지식으로 그럴듯하게 답할 수 있다.
  재측정에서 N2·N3 는 프롬프트가 버텨 정직하게 거부했지만 **구조적 보장이 아니다.**
  ② 속도 — 구 저장소는 무근거 질문이 가장 빨랐다(6.6초). fork 는 LLM 왕복을 그대로 쓴다.

### A-8. 컨텍스트 길이 가드 — ○
- 청크 1건 4,000자 / 총 24,000자. 최대 138,570자짜리 청크가 존재해 8개만 모아도 30만 자가 됐다.
- **fork** 동일.

### A-9. 히스토리 길이 가드 — ✗ **fork 없음**
- **구현** `LLM_HISTORY_CHAR_BUDGET=6000` — 최근 10건을 담되 예산 초과 시 오래된 것부터 버린다.
- **fork** 설정 자체가 없다. 최근 10개를 **글자 제한 없이** 넣는다.
- **영향** 평가는 질문마다 새 대화라 드러나지 않았다. **실사용에서 긴 표 답변이 몇 번 오가면
  히스토리만으로 프롬프트가 수만 토큰이 된다** — 지연·비용 증가, 근거 예산 잠식.

### A-10. 프로젝트 보안 필터 — ○
- `should = [project_id 일치 OR is_global=True]`. `must` 로 걸면 사업 지정 시 법령이 통째로 배제된다.
- **fork** 동일.
- **한계(양쪽 공통)** 프로젝트 미지정 대화에서는 필터가 없어 **타 사업 문서가 섞인다.**
  실측: 안면도 질문에 당진1·임자 약정서가 출처 4·6·8위로 유입.

### A-11. 출처 위치 라벨 (`format_location`) — ○
- xlsx 는 페이지가 시트 순번일 뿐이라 `p.3` 이 무의미 → 시트명·셀범위를 쓴다.
- LLM 컨텍스트와 화면 출처 칩이 **같은 함수**를 써서 어긋나지 않게 한다.
- **fork** 동일.

### A-12. 모델 allowlist — ○
- 클라이언트가 보낸 모델명을 그대로 쓰면 임의의 고가 모델을 호출당한다. `LLM_MODEL_CHOICES`
  안의 것만 통과(terra / sol / luna).
- **fork** 동일(`resolve_model`).

### A-13. 코퍼스 버전 격리 — △ (방식이 다름)
- **구 저장소** `CorpusVersion.is_active` 로 Qdrant 컬렉션을 고른다. 본문은 항상 기본 DB.
- **fork** `services/corpus.py` 레지스트리 — `prod/test/final` 각각 **(PG DB alias + Qdrant 컬렉션)** 쌍.
  최종코퍼스는 `final_corpus` DB + 공용 EC2 의 `re_documents_v2`.
- **영향** fork 방식이 더 낫다(계약 데이터가 든 기본 DB 를 덮어쓰지 않는다). **다만 이 분리 때문에
  A-2 버그가 생겼다** — 본문은 alias 를 타는데 사업명 매핑만 기본 DB 를 봤다.

## B. 응답 전달 (UX) — **fork 에 통째로 없음**

이 영역이 격차가 가장 크다. 검색이 평균 6.6초, 전체 9~10초 걸리는 시스템에서
**사용자가 그 시간을 어떻게 겪는가**가 전부 빠져 있다.

### B-1. SSE 실시간 스트리밍 — ✗
- **구 저장소** `POST /api/conversations/{id}/messages/stream/` → `StreamingHttpResponse`
  (`views.py:724`). 프론트는 `fetch` 로 받아 `delta` 마다 본문을 이어 붙인다
  (`ChatView.tsx:408`, `445`).
- **fork** 채팅 뷰에 스트리밍 액션이 **없다**. 프론트도 `messages/send/` 만 호출한다(`client.ts:54`).
  단 `StreamingHttpResponse` 를 **임포트만 해두고 쓰지 않으며**, `services/llm.py` 에는
  `_stream_completion` 이 **이미 구현돼 있다**(224행).
  → **LLM 계층은 준비돼 있고 뷰·프론트 배선만 없다. 새로 만들 것이 아니라 잇는 작업이다.**
- **영향** 체감 대기가 완전히 다르다. 구 저장소는 첫 토큰까지 **P50 7.97초**(그 뒤로는 글자가
  흐른다). fork 는 10초 내내 아무것도 없다가 답변이 한 번에 나타난다.
  **H2 같은 긴 답변(2,051자)에서는 22초 동안 정지 화면이다.**

### B-2. 진행 단계 표시 — ✗
- **구 저장소** 서버가 SSE `status` 이벤트로 단계를 알려준다:
  `사내 자료를 검색하고 있습니다` → (웹검색 시) `웹을 검색하고 있습니다` → `답변을 작성하고 있습니다`.
  프론트가 `setStage` 로 문구를 바꾼다(`ChatView.tsx:439`).
- **fork** 정적 문구 `답변 생성 중` 하나뿐(`ChatView.tsx:274`).
- **영향** 지금 검색 중인지 생성 중인지 알 수 없다. 느릴 때 "멈춘 건가"와 "원래 이만큼 걸리나"를
  구분하지 못한다.

### B-3. 경과 시간 표시 — ✗
- **구 저장소** 전송 시작부터 초를 세어 단계 문구 옆에 `N초` 로 표시(`ChatView.tsx:238-242`, `609`).
  **단계별로 분리된 타이머가 아니라 누적 경과 시간이고**, 단계 문구가 옆에서 바뀌는 구조다.
- **fork** 없음.
- **영향** B-2 와 합쳐져야 의미가 산다 — "사내 자료를 검색하고 있습니다 · 7초"를 보면
  사용자가 진행 상황을 판단할 수 있다.

### B-4. 출처 먼저 표시 — ✗
- **구 저장소** 스트림에서 `sources` 이벤트를 **`delta` 보다 먼저** 보낸다(`views.py` stream 순서).
  프론트는 답변 글자가 나오기 전에 출처 칩을 먼저 그린다(`ChatView.tsx:442`).
- **fork** 응답이 한 번에 오므로 순서 개념이 없다.
- **영향** 근거를 먼저 보여주면 사용자가 답변을 읽기 전에 신뢰도를 가늠할 수 있다.

### B-5. 답변 복사 버튼 — ✗
- **구 저장소** `copiedId` 상태로 답변별 복사 + 완료 피드백.
- **fork** 없음.

## C. 답변 렌더링 — 전부 이식됨 ○

fork 커밋 `a8c72e1` "채팅 답변 렌더링 — 동료 저장소의 표·차트·도식 컴포넌트 도입"으로
아래가 그대로 들어갔다. **`TableChart.tsx` · `VizBlock.tsx` · `TimelineBlock.tsx` 는 바이트 단위 동일.**

### C-1. 마크다운 + GFM 표 — ○
`react-markdown` + `remark-gfm`, 코드펜스 언어 태그로 렌더러 분기.

### C-2. 표 → 차트 전환 (`TableChart`) — ○
- **설계 원칙** LLM 에게 차트 값을 따로 쓰게 하지 않고, **화면에 이미 있는 표의 DOM 에서 숫자를
  파싱**해 recharts 로 그린다. 표는 차트 모드에서도 DOM 에 남겨 대조 가능.
- **왜** 표는 틀리면 눈에 띄지만 차트는 그럴듯해 보여 더 위험하다.

### C-3. mermaid 도식 (`MermaidBlock`) — △ (fork 가 오히려 개선)
- 스트리밍 중 미완성 코드로 수십 번 호출되므로 `render()` 전에 `parse(suppressErrors)` 로 검사.
- 렌더 전 `document.fonts` 로 Pretendard 로딩 대기 — 폰트 도착 전에 글자 폭을 재면 한글이 잘린다
  (실측: '당진행복솔라 주식회사' → '당진행복솔라 주식호').
- **fork 차이** mermaid 를 **도식이 나올 때만 지연 로드**하도록 개선했다(초기 번들 축소).
  → 이건 fork 쪽을 역으로 가져올 만한 개선이다.

### C-4. `viz:timeline` 전용 컴포넌트 — ○
- mermaid timeline 을 쓰지 않는 이유: 가로 배치라 채팅 폭 820px 에서 이벤트 11개면 판독 불가,
  테마 변수를 무시하고 자체 팔레트를 쓴다.
- LLM 은 JSON 만 내고 **총 기간·완료 건수는 컴포넌트가 직접 계산**한다.
- 스트리밍 중 잘린 JSON 판정은 시간이 아니라 **괄호 균형 검사**로 결정적으로 한다.

### C-5. 조건부 도식 지침 주입 — ○
- `_DIAGRAM_HINTS` 30여 개 표현이 질문에 있을 때만 약 400자 지침을 붙인다.
- **왜** 항상 붙이면 사내 근거 예산을 잠식하고 요청하지 않은 답변에 도식이 끼어든다.
- ASCII 아트 금지 규칙은 실측 사고(‘가시화’ 미감지 → 박스 문자 도식 → 가로 잘림)에서 나왔다.

## D. 부가 기능

### D-1. 웹 검색 토글 — ✗ **fork 없음**
- **구 저장소** `services/web_search.py` + `run_web_search()`. 사용자가 켤 때만 호출하고
  **자동 폴백은 하지 않는다** — 사내 전용 질의에 이름만 비슷한 다른 사업 기사가 올라온 실측 때문.
- 사내 문서와 **명확히 구분된 블록**으로 넣고, 충돌 시 사내 문서 우선 + 충돌 사실 명시를 지시한다.
- **fork** `services/web_search.py` 자체가 없다.

### D-2. 첨부파일 컨텍스트 — △
