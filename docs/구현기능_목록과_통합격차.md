## A. 검색·근거 품질 (백엔드)

### A-1. Qdrant 하이브리드 검색 (dense + sparse) — ○
- **구현** `services/retriever.py` `ExistingQdrantRetriever._get_relevant_documents`
- sparse 로 Prefetch 후 dense 로 최종 정렬. BGE-M3 한 모델이 두 벡터를 동시에 낸다.
- **왜** 고유명사(SPC명·사업명)는 sparse 가, 의미 유사도는 dense 가 잡는다. 한쪽만 쓰면
  "당진행복솔라" 같은 사내 고유명사를 놓친다.
- **중요** 이 구조는 융합이 아니라 **깔때기**다. 최종 결과는 sparse 상위 N 의 부분집합이고
  dense 는 순서만 바꾼다. 그래서 `RAG_PREFETCH_K` 를 `RAG_RETRIEVE_K` 와 같게 두면
  dense 가 무력해진다 → 양쪽 모두 64 / 16 으로 분리(우리 `eeff90d`, fork `b10a800`).
- **fork** 동일.

  질의 시 `services/retriever._rerank_context_header`(리랭커 입력)
- **왜** 문서명에만 신호가 있는 청크가 본문에 질의어가 없다는 이유로 밀렸다.
  **실측: `계약서_설계용역_251231.docx` 의 계약 당사자 조항이 0.117 → 0.835**
- **초판의 fork 버그는 해소됐다** — `_project_label_map()` 이 `db_alias` 를 받도록

  S1 게이트 통과가 1 → 5건으로 회복됐다.
- **남은 문제** `HEADER_SKIP_EXTS` 가 md/txt 를 헤더 주입에서 제외하는데, 이 전제
  ("헤딩에 사업명이 이미 있다")가 청크 단위에서 깨진다. `10. 금융(PF) — 당진1` 청크는
  헤딩에 "당진1"만 있고 질문이 쓰는 "당진행복솔라"가 없다.
  **실측(구 저장소) 헤더 없이 0.2709 → 헤더 붙여 0.6405.**
