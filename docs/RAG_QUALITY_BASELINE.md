## 1. 현재 RAG 핵심 설정

### 1.1 검색 · 벡터 DB

- **하이브리드 검색** — Qdrant `query_points` 의 Prefetch API. sparse 로 후보를 먼저
  긁고(`limit=K`) dense 로 최종 정렬한다. (`services/retriever.py`)
- **본문은 Qdrant 에 없다.** payload 에는 메타데이터만 있고, 검색 후
  `qdrant_point_id` 로 Postgres `document_chunks` 를 일괄 조회해 본문을 채운다.
  → **스냅샷만으로는 RAG 가 안 돈다. PG 덤프와 쌍이어야 한다.**
- **보안 필터** — 대화에 프로젝트가 지정되면
  `should = [project_id 일치 OR is_global=True]`. `must` 로 걸지 않는 이유는
  사내 문서와 법령 근거를 함께 요구하는 질문이 많기 때문이다.

### 1.2 top-k · 리랭킹 · 게이트

| 설정 | 값 | 의미 |
|---|---:|---|
| `RAG_RETRIEVE_K` | 16 | Qdrant 1차 후보 수 |
| `RAG_MAX_CONTEXT_K` | 8 | LLM 에 넣을 최종 청크 수 |
| `RERANK_BACKEND` | `openvino_int8` | 실패 시 torch 로 자동 폴백 |
| `RERANK_MAX_LENGTH` | 384 | 768 과 순위가 같고 지연은 절반(실측) |
| `RERANK_SKIP_MARGIN` | 0.25 | 경계 점수차가 이보다 크면 리랭킹 생략 |
| `RAG_GATE_MIN_TOP1_RERANK` | 0.55 | 1위가 이 미만이면 **전부 버리고 '자료 없음'** |
| `RAG_GATE_REL_MARGIN_RERANK` | 0.12 | 1위에서 이만큼 떨어진 꼬리를 컷 |
| `RAG_CONTEXT_CHUNK_CHAR_LIMIT` | 4,000 | 청크 1건 상한 |
| `RAG_CONTEXT_CHAR_BUDGET` | 24,000 | 컨텍스트 총 예산 |
| `LLM_HISTORY_CHAR_BUDGET` | 6,000 | 히스토리 최대 10건 + 글자 예산 |

**컨텍스트 헤더** `[사업: X] [문서: Y]` 를 임베딩 입력과 **리랭커 입력 양쪽**에 붙인다.
문서명에만 신호가 있는 청크가 밀리던 문제를 고친 것이다(실측 0.117 → 0.835).
md·txt 는 헤딩에 이미 사업명이 있어 건너뛴다(`HEADER_SKIP_EXTS`).

**중복 제거** — 정렬 후·컷 전에 공백 정규화 완전일치 청크를 제거한다. 근사 중복은
일부러 묶지 않는다(다른 사업의 유사 조항이 하나로 합쳐질 위험).

### 1.3 컨텍스트 구성

```
[참고자료 1] {문서제목} ({위치라벨})
{청크 본문 — 4,000자 초과 시 절단}

[참고자료 2] ...
```
위치라벨은 xlsx 면 `시트: 이름 (범위)`, 그 외는 `p.N · 절 제목`.

### 1.4 시스템 프롬프트 (요지)

```
당신은 재생에너지(태양광/풍력) 분야의 전문 지식을 갖고 있는 사업개발실의 사내 AI 에이전트입니다.
한국어로 친절하고 격식 있게 답변하십시오.
주어진 [사내 참고 문서 내용]을 기반으로만 사용자의 질문에 대답하십시오.
답변은 반드시 참고 자료의 사실에 근거해야 하며, 참고 자료에 없는 내용은 절대 지어내거나
가상의 수치, 예측값 등을 임의로 만들어 대답하지 마십시오.
가설적인 추론이나 없는 사실을 꾸며내는 행위는 완전히 금지됩니다.
자료가 부족해 정확한 대답을 할 수 없다면 솔직히 모른다고 답변하십시오.

[사내 참고 문서 내용]
{context}
```
- 도식 지침(약 400자)은 질문에 도식·차트 요청 표현이 있을 때만 덧붙인다.
- 웹 검색을 켠 경우에만 별도 블록으로 웹 근거를 구분해 넣는다.

> 통합 저장소는 시스템 프롬프트가 **다르다**(‘재생E AI Agent’ + 마크다운 서식 규칙).
> 품질 점수가 달라지면 검색 탓인지 프롬프트 탓인지부터 갈라야 한다.

### 1.5 LLM

| 항목 | 값 |
|---|---|
| 모델 | `gpt-5.6-terra` (allowlist: terra / sol / luna) |
| temperature | 0.3 요청 → **모델이 거부해 파라미터 제거 후 재시도**(추론 모델은 기본값 1만 허용) |
| max_completion_tokens | 4,096 |
| 타임아웃 | 180초 (connect 10초) |

### 1.6 전체 흐름

```
질문
 → 임베딩(BGE-M3 dense+sparse)
 → Qdrant 하이브리드 검색 (K=16, 프로젝트 필터)
 → Postgres 에서 청크 본문 채우기
 → 조건부 리랭킹 (경계가 모호할 때만)
 → 완전일치 중복 제거
 → 관련성 게이트  ──(1위 < 0.55)──▶ LLM 호출 없이 "관련 자료를 찾지 못했습니다"
 → 상위 8건 컷 → 컨텍스트 조립(예산 24,000자)
 → 시스템 프롬프트 + 최근 히스토리 + 질문
 → LLM 스트리밍 응답 → 출처 칩
```

## 2. 재현 방법

```bash
docker exec re_backend python manage.py eval_rag_baseline --out /app/media/rag_baseline.json
```

- 하니스: [`backend/apps/rag/management/commands/eval_rag_baseline.py`](../backend/apps/rag/management/commands/eval_rag_baseline.py)
- 평가셋: [`backend/apps/rag/management/commands/rag_eval_questions.json`](../backend/apps/rag/management/commands/rag_eval_questions.json)
- 실제 HTTP 엔드포인트를 호출하므로 **시스템 프롬프트가 바뀌어도 측정과 서비스가 어긋나지 않는다.**
- 질문마다 새 대화를 만들고, 끝나면 그 대화들만 지운다(`--keep-conversations` 로 보존).
- 통합 저장소용 옵션: `--corpus final` (코퍼스 키), `--user-email`, `--model`.
  엔드포인트·인증(세션/JWT)·LLM 함수 이름은 있는 것을 찾아 쓴다.

### 측정 방식 정의 (이 정의를 바꾸면 비교 불가)

| 지표 | 정의 |
|---|---|
| **검색(retrieval)** | `retrieve_for_views()` 진입~반환. 임베딩 + Qdrant + 리랭킹 + 중복제거 |
| **TTFT** | 요청 시작 ~ **첫 delta 토큰** 도착. 사용자 체감 대기 |
| **합계(total)** | 요청 시작 ~ SSE 스트림 종료 |
| 워밍업 | 첫 1회(모델 로드 30초대)는 버린다 |
| 시계 | `time.perf_counter()` · 백엔드 컨테이너 내부(브라우저 왕복 제외) |
| 반복 | 질문당 1회 (`--repeat N` 으로 늘릴 수 있음) |

## 3. 평가 기준 (1~5점)

| 축 | 5점 | 3점 | 1점 |
|---|---|---|---|
| **Correctness** | 사실이 원문과 완전 일치 | 일부만 맞거나 불확실 표기 누락 | 틀렸거나 답을 못 냄 |
| **Groundedness** | 모든 진술이 제시된 출처에 있음 | 대체로 근거하나 귀속·범위가 흐림 | 출처에 없는 진술 |
| **Relevance** | 질문에 정확히 답함 | 주변 정보로 겉돎 | 질문과 무관 |
| **Retrieval Quality** | 정답 문서가 상위에 옴 | 정답 문서가 있으나 묻힘 | 정답 문서가 후보에 없음 |
| **Completeness** | 물어본 항목을 다 채움 | 일부 누락 | 대부분 누락 |
| **Hallucination** | 없음 / 부분(귀속 오인) / 있음(수치·사실 날조) — 점수 대신 3단계 |
| **Response Time** | 아래 PASS/WARN/FAIL 기준 |

> 무근거 질문(N 계열)의 **정답은 “자료에 없다”** 이다. 모른다고 답하면 Correctness 5.

| N3 | 6.65 | 6.67 | 6.67 | 0 | 16/0 |

| 구간 | 평균 | P50 | P95 | 최소 | 최대 |
|---|---:|---:|---:|---:|---:|
| **합계** | 9.25 | 8.67 | 17.06 | 6.64 | 17.06 |

> 임베딩·리랭킹을 봐야 한다. 합계의 최대값(17.06초)은 답변이 길어서지 검색이 느려서가 아니다.

## 5. PASS / WARNING / FAIL 기준

재측정 결과를 이 표에 대입한다. **하나라도 FAIL 이면 통합 회귀로 본다.**

### 5.1 품질

| 항목 | PASS | WARNING | FAIL |
|---|---|---|---|
| Correctness 평균 | ≥ 4.0 | 3.5 ~ 4.0 | < 3.5 |
| Groundedness 평균 | ≥ 4.5 | 4.0 ~ 4.5 | < 4.0 |
| Relevance 평균 | ≥ 4.5 | 4.0 ~ 4.5 | < 4.0 |
| Retrieval Quality 평균 | ≥ 3.5 | 3.0 ~ 3.5 | < 3.0 |
| Completeness 평균 | ≥ 4.0 | 3.5 ~ 4.0 | < 3.5 |
| 심각 환각(없는 수치·사실 날조) | 0건 | 1건 | 2건 이상 |
| **핵심 회귀 5문항**(F1·F2·F3·G2·H1) | 전부 Correctness 5 | 1건이 4 | 1건이라도 ≤ 3 |
| **무근거 차단**(N2·N3) | 2건 모두 출처 0 + 고정응답 | 1건만 차단 | 둘 다 차단 실패 |

### 5.2 속도 (Baseline 대비)

| 항목 | Baseline | PASS | WARNING | FAIL |
|---|---:|---|---|---|
| 합계 P50 | 8.67s | ≤ 10.4s (+20%) | ≤ 13.0s (+50%) | > 13.0s |
| 합계 P95 | 17.06s | ≤ 20.5s | ≤ 25.6s | > 25.6s |
| 검색 P50 | 6.66s | ≤ 8.0s | ≤ 10.0s | > 10.0s |
| TTFT P50 | 7.97s | ≤ 9.6s | ≤ 12.0s | > 12.0s |

> 속도는 하드웨어·네트워크에 따라 흔들린다. **FAIL 이 속도에서만 나오면
> 코드 회귀로 단정하지 말고** 같은 기계에서 한 번 더 재고 판단한다.

## 6. 통합 프로젝트에서 재검증하는 방법

1. **하니스와 평가셋 2개 파일을 그대로 복사한다.**
   `backend/apps/rag/management/commands/eval_rag_baseline.py`
   `backend/apps/rag/management/commands/rag_eval_questions.json`
   → 질문을 고치면 이 문서와 비교할 수 없다. 추가만 하고 기존 id 의 문장은 건드리지 않는다.

2. **실행** (통합 저장소는 최종코퍼스 키를 넘겨야 한다)
   ```bash
   docker exec re_backend python manage.py eval_rag_baseline --corpus final \
       --out /app/media/rag_after_merge.json
   ```

3. **먼저 환경 차이부터 적는다.** 아래가 다르면 숫자 차이의 원인이 코드가 아닐 수 있다.

   | 항목 | Baseline(이 문서) | 통합 저장소(2026-09-15 기준) |
   |---|---|---|
   | Qdrant | 로컬 컨테이너 | **공용 EC2 · HTTPS** (`resaiagent-vecdata.duckdns.org`) |
   | 청크 본문 DB | `default`(`re_agent`) | `final_corpus`(`re_agent_final`) |
   | 시스템 프롬프트 | 위 1.4 | **다름** — ‘재생E AI Agent’ + 마크다운 서식 규칙 |
   | 무근거 분기 | 게이트 탈락 시 LLM 미호출 고정응답 | 고정응답 분기 **없음** — 컨텍스트만 비우고 LLM 호출 |

   > 마지막 줄이 특히 중요하다. 통합 쪽은 근거가 없을 때 **일반 지식으로 답할 수 있어**
   > N2·N3 에서 출처 0건인데 그럴듯한 답이 나올 수 있다. 그건 속도가 아니라 **환각 축에서
   > FAIL** 로 잡아야 한다.
   >
   > 참고 실측: 통합 저장소(공용 Qdrant, HTTPS)에서 F1·F2 검색 구간은 6.94s·6.27s 로
   > 본 Baseline(6.66s·5.93s)과 큰 차이가 없었다. 네트워크가 병목은 아니다.

4. **5장 표에 대입해 PASS/WARNING/FAIL 을 적고, FAIL 이면 아래 순서로 원인을 가른다.**
   - 출처 목록이 Baseline 과 같은가 → 다르면 **검색 문제**(컬렉션·DB·필터·헤더 주입)
   - 출처는 같은데 답이 다른가 → **프롬프트/모델 문제**
   - 게이트 사유(`gate` 필드)가 다른가 → **임계값 설정 문제**
   - 출처가 0건인데 답이 길다 → **본문 조회 실패**(PG 스키마·DB alias). 결과 JSON 의
     `source_count` 와 `answer_chars` 를 같이 본다.
