## 1. 현재 RAG 핵심 설정

### 1.1 검색 · 벡터 DB

- **하이브리드 검색** — Qdrant `query_points` 의 Prefetch API. sparse 로 후보를 먼저
  긁고(`limit=K`) dense 로 최종 정렬한다. (`services/retriever.py`)
- **본문은 Qdrant 에 없다.** payload 에는 메타데이터만 있고, 검색 후
  `qdrant_point_id` 로 Postgres `document_chunks` 를 일괄 조회해 본문을 채운다.
  → **스냅샷만으로는 RAG 가 안 돈다. PG 덤프와 쌍이어야 한다.**
- **보안 필터** — 대화에 프로젝트가 지정되면
  `should = [project_id 일치 OR is_global=True]`. `must` 로 걸지 않는 이유는
  사내 문서와 법령 근거를 함께 요구하는 질문이 많기 때문이다.

### 1.2 top-k · 리랭킹 · 게이트

| 설정 | 값 | 의미 |
|---|---:|---|
| `RAG_RETRIEVE_K` | 16 | Qdrant 1차 후보 수 |
| `RAG_MAX_CONTEXT_K` | 8 | LLM 에 넣을 최종 청크 수 |
| `RERANK_BACKEND` | `openvino_int8` | 실패 시 torch 로 자동 폴백 |
| `RERANK_MAX_LENGTH` | 384 | 768 과 순위가 같고 지연은 절반(실측) |
| `RERANK_SKIP_MARGIN` | 0.25 | 경계 점수차가 이보다 크면 리랭킹 생략 |
| `RAG_GATE_MIN_TOP1_RERANK` | 0.55 | 1위가 이 미만이면 **전부 버리고 '자료 없음'** |
| `RAG_GATE_REL_MARGIN_RERANK` | 0.12 | 1위에서 이만큼 떨어진 꼬리를 컷 |
| `RAG_CONTEXT_CHUNK_CHAR_LIMIT` | 4,000 | 청크 1건 상한 |
| `RAG_CONTEXT_CHAR_BUDGET` | 24,000 | 컨텍스트 총 예산 |
| `LLM_HISTORY_CHAR_BUDGET` | 6,000 | 히스토리 최대 10건 + 글자 예산 |

**컨텍스트 헤더** `[사업: X] [문서: Y]` 를 임베딩 입력과 **리랭커 입력 양쪽**에 붙인다.
문서명에만 신호가 있는 청크가 밀리던 문제를 고친 것이다(실측 0.117 → 0.835).
md·txt 는 헤딩에 이미 사업명이 있어 건너뛴다(`HEADER_SKIP_EXTS`).

**중복 제거** — 정렬 후·컷 전에 공백 정규화 완전일치 청크를 제거한다. 근사 중복은
일부러 묶지 않는다(다른 사업의 유사 조항이 하나로 합쳐질 위험).

### 1.3 컨텍스트 구성

```
[참고자료 1] {문서제목} ({위치라벨})
{청크 본문 — 4,000자 초과 시 절단}

[참고자료 2] ...
```
위치라벨은 xlsx 면 `시트: 이름 (범위)`, 그 외는 `p.N · 절 제목`.

### 1.4 시스템 프롬프트 (요지)

```
당신은 재생에너지(태양광/풍력) 분야의 전문 지식을 갖고 있는 사업개발실의 사내 AI 에이전트입니다.
한국어로 친절하고 격식 있게 답변하십시오.
주어진 [사내 참고 문서 내용]을 기반으로만 사용자의 질문에 대답하십시오.
답변은 반드시 참고 자료의 사실에 근거해야 하며, 참고 자료에 없는 내용은 절대 지어내거나
가상의 수치, 예측값 등을 임의로 만들어 대답하지 마십시오.
가설적인 추론이나 없는 사실을 꾸며내는 행위는 완전히 금지됩니다.
자료가 부족해 정확한 대답을 할 수 없다면 솔직히 모른다고 답변하십시오.

[사내 참고 문서 내용]
{context}
```
- 도식 지침(약 400자)은 질문에 도식·차트 요청 표현이 있을 때만 덧붙인다.
- 웹 검색을 켠 경우에만 별도 블록으로 웹 근거를 구분해 넣는다.

> 통합 저장소는 시스템 프롬프트가 **다르다**(‘재생E AI Agent’ + 마크다운 서식 규칙).
> 품질 점수가 달라지면 검색 탓인지 프롬프트 탓인지부터 갈라야 한다.

### 1.5 LLM

| 항목 | 값 |
|---|---|
| 모델 | `gpt-5.6-terra` (allowlist: terra / sol / luna) |
| temperature | 0.3 요청 → **모델이 거부해 파라미터 제거 후 재시도**(추론 모델은 기본값 1만 허용) |
| max_completion_tokens | 4,096 |
| 타임아웃 | 180초 (connect 10초) |

### 1.6 전체 흐름

```
질문
 → 임베딩(BGE-M3 dense+sparse)
 → Qdrant 하이브리드 검색 (K=16, 프로젝트 필터)
 → Postgres 에서 청크 본문 채우기
 → 조건부 리랭킹 (경계가 모호할 때만)
 → 완전일치 중복 제거
 → 관련성 게이트  ──(1위 < 0.55)──▶ LLM 호출 없이 "관련 자료를 찾지 못했습니다"
 → 상위 8건 컷 → 컨텍스트 조립(예산 24,000자)
 → 시스템 프롬프트 + 최근 히스토리 + 질문
 → LLM 스트리밍 응답 → 출처 칩
```

## 2. 재현 방법

```bash
docker exec re_backend python manage.py eval_rag_baseline --out /app/media/rag_baseline.json
```

- 하니스: [`backend/apps/rag/management/commands/eval_rag_baseline.py`](../backend/apps/rag/management/commands/eval_rag_baseline.py)
- 평가셋: [`backend/apps/rag/management/commands/rag_eval_questions.json`](../backend/apps/rag/management/commands/rag_eval_questions.json)
- 실제 HTTP 엔드포인트를 호출하므로 **시스템 프롬프트가 바뀌어도 측정과 서비스가 어긋나지 않는다.**
- 질문마다 새 대화를 만들고, 끝나면 그 대화들만 지운다(`--keep-conversations` 로 보존).
- 통합 저장소용 옵션: `--corpus final` (코퍼스 키), `--user-email`, `--model`.
  엔드포인트·인증(세션/JWT)·LLM 함수 이름은 있는 것을 찾아 쓴다.

### 측정 방식 정의 (이 정의를 바꾸면 비교 불가)

| 지표 | 정의 |
|---|---|
| **검색(retrieval)** | `retrieve_for_views()` 진입~반환. 임베딩 + Qdrant + 리랭킹 + 중복제거 |
| **TTFT** | 요청 시작 ~ **첫 delta 토큰** 도착. 사용자 체감 대기 |
| **합계(total)** | 요청 시작 ~ SSE 스트림 종료 |
| 워밍업 | 첫 1회(모델 로드 30초대)는 버린다 |
| 시계 | `time.perf_counter()` · 백엔드 컨테이너 내부(브라우저 왕복 제외) |
| 반복 | 질문당 1회 (`--repeat N` 으로 늘릴 수 있음) |

## 3. 평가 기준 (1~5점)

| 축 | 5점 | 3점 | 1점 |
|---|---|---|---|
| **Correctness** | 사실이 원문과 완전 일치 | 일부만 맞거나 불확실 표기 누락 | 틀렸거나 답을 못 냄 |
| **Groundedness** | 모든 진술이 제시된 출처에 있음 | 대체로 근거하나 귀속·범위가 흐림 | 출처에 없는 진술 |
| **Relevance** | 질문에 정확히 답함 | 주변 정보로 겉돎 | 질문과 무관 |
| **Retrieval Quality** | 정답 문서가 상위에 옴 | 정답 문서가 있으나 묻힘 | 정답 문서가 후보에 없음 |
| **Completeness** | 물어본 항목을 다 채움 | 일부 누락 | 대부분 누락 |
| **Hallucination** | 없음 / 부분(귀속 오인) / 있음(수치·사실 날조) — 점수 대신 3단계 |
| **Response Time** | 아래 PASS/WARN/FAIL 기준 |

> 무근거 질문(N 계열)의 **정답은 “자료에 없다”** 이다. 모른다고 답하면 Correctness 5.

### 4.5 문서당 상한(`RAG_MAX_CHUNKS_PER_DOC=4`) 도입 (2026-09-21)

**§7 결함 1(후보 독식)의 진단이 틀렸다는 것이 이 작업에서 드러났다.**
"정답 문서가 후보에 못 든다"고 적었으나, 단계별로 추적하니 **들어와 있었다.**

G1 `홍성 설계 인허가 용역 어떤 업체에서 하는데?` · 정답 `계약서_설계용역_251231.docx`:

| 단계 | 정답 위치 |
|---|---|
| sparse 상위 64 | **34위** (5청크) — 들어옴 |
| dense 재정렬 → 64 | **41위** (5청크) — 여전히 있음 |
| dense 재정렬 → **16** (`RAG_RETRIEVE_K`) | **탈락** |
| 리랭킹 | **보지도 못함** |

기존 기록의 "prefetch 200 에서도 미진입"은 **리랭킹까지 끝난 목록**을 본 것이라
후보 진입 여부가 아니었다. 실제로는 sparse 34위다.

**16칸이 단 2종 문서로 채워져 있었다** — 공정표 6 + 착수보고자료 9 + 1.
큰 표가 조각날 때 조각마다 표 헤더가 다시 붙어(`chunkers._continuation_heading`)
서로 거의 같은 텍스트로 시작하고, 그래서 비슷한 점수로 함께 올라온다.
(문서별 청크 수: 공정표 20 · 착수보고자료 58 · 계약서 32)

**상한 4를 걸자 정답이 1위(0.8088)로 들어왔다** — 공정표 최고점 0.7762 보다 높다.
리랭커는 처음부터 알아볼 수 있었고 기회가 없었을 뿐이다.

| 상한 | 컨텍스트 8칸의 고유 문서 | 정답 위치 |
|---:|---:|---|
| 없음 | 2종 | 없음 |
| 6 | 3종 | 없음 |
| **4** | **4종** | **1위 · 5위** |
| 3 | 5종 | 3위 · 6위 |

**낮을수록 좋은 값이 아니다.** 6은 못 들여왔고 3은 정답을 3위로 밀었다.
G2 사업개요·H2 사업성검토처럼 한 문서가 정말 여러 조각으로 답해야 하는 질의가
실제로 4칸까지 쓰므로 그 아래로 내리면 그쪽이 깎인다.

**12문항 중 출처가 바뀐 것은 G1 하나뿐이다.** 나머지 11문항은 출처 구성이 동일하다.

> **⚠ 그런데 G1 답변은 여전히 "확인되지 않습니다" 다.** 문서는 들어왔지만
> **업체명이 든 청크가 아니다.** 들어온 것은 `p.98 · 표 1`(용역명은 있으나 계약자명 없음)이고,
> `주식회사 유신` 이 적힌 것은 89자짜리 `전문` 청크(`chunk_index=0`)인데 **후보에 오지 못한다.**
> → **§7 결함 7.** 상한은 "문서 진입"을 고쳤지 "그 문서의 어느 청크가 오는가"는 고치지 않았다.
>
> **⚠ 초판 정정.** 여기 한때 "그 청크는 리랭커 점수가 0.1170 이라 안 뽑힌다"고 적었다. **틀렸다.**
> 그 0.1170 은 진단 스크립트가 **컨텍스트 헤더 없이** 본문만 채점한 값이다. 실제 파이프라인은

> 통합 저장소가 헤더를 붙여 재서 **0.6973** 을 얻었다 — **리랭커는 이 청크를 높게 본다.**

## 7. 이 Baseline 이 드러낸 알려진 결함 (통합 전에도 이미 있던 것)

고칠 대상이지 회귀가 아니다. 통합 후에도 **그대로면 정상**, 더 나빠지면 회귀다.

| # | 증상 | 근거 | 성격 |
|---|---|---|---|
| 1 | ~~**후보 독식** — 정답 문서가 후보에 못 든다~~ → **진단이 틀렸다. 조치 완료** | 정답은 sparse 34위로 **후보 안에 있었고** `RAG_RETRIEVE_K=16` 에서 잘렸다. `RAG_MAX_CHUNKS_PER_DOC=4` 로 1위 진입(0.8088). **§4.5 참조** | 검색 |
| 7 | **짧은 정답 청크가 sparse 에서 바닥으로 깔린다** | G1: `주식회사 유신` 이 적힌 89자 `전문` 청크가 **sparse 565위**(limit 600) · dense 71위. 리랭커는 **0.6973** 으로 높게 보는데 **도달하지 못한다**. 답변은 여전히 "확인되지 않습니다" | 검색 |
| 8 | **S2 정답 표가 sparse·dense·리랭커 **셋 다**에서 바닥** | `계약서_대출약정서_20240703.docx` 의 대주단 표가 리랭커 **0.0012**(floor 의 1/125), dense 600에서 265위, sparse 600에서 369위 | 검색 |
| 9 | **docx 표가 문서 끝으로 밀리고 절 제목이 `표 N` 으로 덮인다** | `parser.py:281` 주석이 이미 인정 — "위치 보존은 한계 인정(문서 말미 배치)". 「부록 I 대주들의 대출약정금」이 `표 2` 가 된다 | **적재** |

**결함 1·7·8 과 사례 3 은 모두 같은 구조다** — dense 는 찾아내는데 sparse 가 관문이라
못 들어온다. 결함 1만 `RAG_MAX_CHUNKS_PER_DOC` 로 풀렸고(후보 안에는 있었으므로),
7·8 은 prefetch 단계에서 이미 없어 **융합 방식(RRF/DBSF) 변경이 필요하다.**
이것이 지금 가장 큰 단일 과제다.

### 결함 8 — S2 의 정답 문서가 후보에 0칸 (2026-09-21)

**S2 는 답이 있는 질문이다.** 사업개요 `10. 금융(PF)` 절이 전부 '미정'인 것은
**그 요약표가 안 채워진 것**이지 대주단이 정해지지 않은 것이 아니었다.

근거는 `계약서_대출약정서_20240703.docx`(257청크)다. 원본 docx 를 직접 열어 확인했다 —
`당진행복솔라` 90회 · `우리은행` 121회 · `교보생명` 12회 · `Tranche` 168회.

**가장 좋은 근거 청크는 `부록 I — 대주들의 대출약정금` 이다.** 서명란이 아니라 이쪽이
S2 가 묻는 "대주단 구성을 **표로**"에 그대로 대응한다.

| Tranche | 대주명 | 대출약정금 | 약정비율 |
|---|---|---:|---:|
| A | 주식회사 우리은행 | 500억 | 37.04% |
| B | 교보생명보험 주식회사 | 500억 | 37.04% |
| C | 주식회사 우리은행 | 350억 | 25.92% |
| D | 추후 확정 | — | — |
| **합계** | | **1,350억** | **100.0%** |

#### ⚠ 정정 — 이 표는 문서 끝에 `표 2` 라는 이름으로 떨어져 있다

처음엔 "`부록 I` 청크가 답"이라고 적었으나 **본문 위치에 그 표가 없다.**
`chunk_index=102` 는 `부록 I … 1. 대주들의 대출약정금 / 2. 각 대주의 통지처` 라는
**목차 줄만** 남기고 끝나고, 실제 표는 **`chunk_index=218` · 절 `표 2`** 로 문서 끝에 있다.
원인은 **결함 9**다.

**아래 "dense 3위"도 정답 표가 아니다** — 그 3위는 같은 **문서**의 다른 청크(서명란 등)였다.
정답 표 자체를 재면 셋 다 바닥이다.

| 단계 | 정답 표(idx=218) |
|---|---|
| sparse 64 / 200 | 미진입 (600에서 **369위**) |
| **dense 64 / 200** | **미진입** (600에서 **265위**) |
| 하이브리드 64 / 200 | 미진입 (600에서 28위) |
| **리랭커** | **0.0012** — floor 0.15 의 **1/125** |

**사례 3·결함 7 과 다르다.** 거기선 dense 가 정답을 알아봤다. 여기선 **dense 도 못 알아보고,
도달시켜도 리랭커가 버린다.**

절 제목을 복원해 넣는 실험(통합 저장소 실측):

| 리랭커 입력 앞머리 | 점수 |
|---|---:|
| 현재 `[문서: 계약서_대출약정서_20240703]` | 0.0012 |
| `[사업: 당진1PJT]` | 0.0289 |
| `[사업: 당진1PJT 당진행복솔라] … 부록 I 대주들의 대출약정금 및 통지처` | **0.0978** |

**80배를 올려도 floor 를 못 넘는다.** 같은 모양의 표(`첨부2. 대주별인출금액.pdf` 등)도
0.0045~0.0124 다. **맨 숫자 표에는 질의어와 겹치는 낱말이 거의 없다.**

**→ 융합(RRF/DBSF)만으로는 안 풀린다.** 필요한 것은 셋이다 —
① 융합 ② **결함 9 수정(적재 단계)** ③ 표 청크의 관련성 판정 방식.
**⚠ floor 를 내려서 때우지 말 것** — N2(0.0033)·N3(0.0422) 차단이 무너진다.

**아래는 처음 측정한 것으로, 정답 표가 아니라 문서 전체 기준이다(기록으로 남긴다).**

| 단계 | 대출약정서가 먹은 칸 | 최상위 |
|---|---|---|
| sparse limit=64 / 200 | **0칸** | — |
| sparse limit=600 | 21칸 | 291위 |
| dense limit=200 | 5칸 | 3위 |
| 하이브리드 prefetch=64 / 200 | **0칸** | — |

**dense 가 3위로 알아보는 문서가 하이브리드 후보 16칸에 한 칸도 못 든다.**
당진 금융 문서 후보 청크 230건을 전부 채점한 결과 최고 **0.5493** — floor(0.15)를
한참 넘는다. 점수 문제가 아니라 **진입 문제**다.

> **⚠ 개인정보 주의.** `부록 I` 의 2절 「각 대주의 통지처」에는 은행 담당자의 **실명·직위·
> 전화번호·이메일**이 들어 있다. 이 청크가 후보에 들어오면 그대로 **LLM 컨텍스트로 나가고
> 화면 출처 칩에도 뜬다.** 사내 문서라 문제없을 수도 있으나, 후보 진입을 고치기 전에
> **사내 규정 확인이 필요하다.** [[res-agent-ocr-privacy-decision]] 과 같은 계열의 판단이다.

### 결함 9 — docx 표가 문서 끝으로 밀리고 절 제목이 `표 N` 으로 덮인다

**우리 코드에 이미 적혀 있던 한계다.** `backend/services/parser.py:281`:

```python
# 표(Table) 파싱 — Markdown 직렬화 (전략 §3.6). 위치 보존은 한계 인정(문서 말미 배치),
```

`python-docx` 의 `doc.paragraphs` 와 `doc.tables` 는 **별도 컬렉션**이다. 지금 코드는
본문 단락을 모두 훑은 뒤 **표를 전부 문서 끝에 덧붙이고**, `section_title` 을
`f"표 {table_idx+1}"` 로 덮는다(`parser.py:291`, `305`).

**그래서 두 가지가 동시에 사라진다.**
1. **위치** — 표가 어느 절에 속했는지 모른다. 「부록 I 대주들의 대출약정금」이 `표 2` 가 된다.
2. **맥락** — 리랭커 헤더(`_rerank_context_header`)와 화면 출처 라벨(`format_location`)이
   **`표 2` 라는 무의미한 문자열**을 받는다.

**docx 는 단락도 마찬가지다** — `section_title` 이 `f"섹션 {section_idx}"` 다(`parser.py:261`).
즉 **docx 문서에는 의미 있는 절 제목이 하나도 없다.** 코퍼스에서 docx 비중이 얼마인지는
아직 세지 않았다 — 재야 한다.

**부수 피해: 출처 위치 라벨이 실제 페이지가 아니다.** `page_number` 가 단락은 `section_idx`,
표는 `section_idx + 1` 부터 올라가는 **합성 카운터**다. 화면에 `p.98` 로 뜨지만 문서의
98쪽이 아니다.

**고치는 법** `doc.element.body` 를 **문서 순서대로** 순회해 `w:p` → 단락, `w:tbl` → 표로
처리하면 위치가 보존되고, 표 **직전 헤딩**을 절 제목으로 쓸 수 있다.

**⚠ 재적재가 필요하다** — 청크 본문과 메타데이터가 함께 바뀐다. 그리고 **이것만으로는
결함 8이 풀리지 않는다**(제목을 최대로 복원해도 0.0978 < floor 0.15).
그래도 **코퍼스 전체의 표 맥락을 되살리는 일**이라 그 자체로 값이 있고,
결함 1(표 조각 독식)의 헤더 재부착 품질도 함께 올라간다.

### 2026-09-21 추가 — 6번의 근거와 미조치 사유

`HEADER_SKIP_EXTS` 는 "md 는 헤딩에 이미 사업명이 있다"는 전제로 리랭커 헤더 주입을
건너뛴다. **이 전제가 청크 단위에서 깨진다.** 문제의 청크 헤딩은 `10. 금융(PF) — 당진1` 이라
"당진1"은 있지만 질문이 쓰는 **"당진행복솔라"가 없다.** 별칭이 이어지지 않는다.

구 저장소 실측(`당진행복솔라 PF 대주단 구성을 표로 보여줘`):

```
후보 1위  0.4904  보고서_FS보고서최종_20240708.docx / 서문
문제 청크        0. 사업개요_당진1.md / 10. 금융(PF) — 당진1  (572자)
   헤더 없이  0.2709   ← 현재. prefetch 64 에서 후보 미진입, 200 에서 4위, 600 에서 21위
   헤더 붙여  0.6405   ← 붙였다면 1위를 제쳤을 순위 변화
```

> **⚠ 2026-09-21 정정 — 이 청크는 "정답 청크"가 아니다.**
> 원문(`backend/media/initial_docs/2. 당진1PJT/0. 사업개요_당진1.md`)을 직접 열어 확인했다.
> `10. 금융(PF)` 절은 **10개 항목이 전부 `미정 / 미확정`** 이다.
>
> ```
> | PF 대주단 구성       | 미정 | 미확정 | | |
> | 대주별 약정금액·약정비율 | 미정 | 미확정 | | |
> ```
>
> 앞서 "'대주단' 포함=True" 라고 적은 것은 **표의 항목명에 그 낱말이 있다**는 뜻이었지
> 값이 있다는 뜻이 아니었다. 통합 저장소도 자기 코퍼스에서 같은 것을 확인했다.
>
> **한때 "S2 의 정답은 아직 정해지지 않았을 수 있다"고 적었으나, 찾아보니 답이 있다.**
> 사업개요의 요약표가 안 채워진 것이지 대주단이 미정인 것이 아니었다.
> **`expect_grounded: True` 를 유지한다.** 근거는 §7 결함 8 참조.
>
> 아래 0.2709 → 0.6405 는 **순위 관측으로는 여전히 유효하다**(md 헤더 생략이 별칭을
> 못 잇는다). 다만 **그 근거로 우선순위를 높이면 안 된다.**

**⚠ "헤더는 항상 이득"이라는 뜻이 아니다.** 같은 파일의 `2. SPC 정보` 청크는 fork 측정에서

**미조치 사유** `HEADER_SKIP_EXTS` 를 바꾸면 md 청크 전체의 점수가 이동하고, 그러면

동반해 한 번에 가는 것이 맞다.**

~~**참고 — 1번은 한도로 풀리지 않는다.** G1 의 정답 `계약서_설계용역_251231.docx` 는
